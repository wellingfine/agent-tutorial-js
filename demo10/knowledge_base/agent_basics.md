# Agent 基础

Agent 不是简单的一问一答程序。普通聊天机器人通常只根据当前用户输入生成回复，而 Agent 会围绕一个目标持续工作。二者的差别不在于模型是否更强，而在于有没有“目标、状态和循环”。

## 一个最小 Agent 的四个部分

一个最小 Agent 通常包含四个部分：

- 模型：负责理解用户目标、推理下一步、生成回复。
- 消息：保存系统提示词、用户消息、助手消息和工具结果。
- 工具：让模型能够执行外部动作，例如读文件、写文件、查询数据库。
- 运行时：负责把模型、消息、工具和状态组织成一个循环。

这四个部分缺一不可。只有模型而没有循环，那是一次 API 调用；有循环而没有工具，模型只能在自己的上下文里打转；有工具而没有消息记录，模型就看不到上一轮动作的结果，无法继续推进。

## 与聊天机器人的关键差异

普通聊天机器人是“输入到输出”的映射：用户问一句，模型答一句，答完即止。它不保存长期目标，也不会主动去获取它不知道的信息。

Agent 则是一个持续运行的循环：它先理解目标，再决定是否需要调用工具，然后观察工具返回的结果，接着判断目标是否已经达成，没有达成就继续下一轮。这个过程会一直重复，直到满足停止条件。

因此，评价一个 Agent 时，重点不是单次回答是否漂亮，而是它能否在若干轮动作之后把一个模糊目标推进到可交付的结果。

## Agent 的能力边界

Agent 并不是万能的，它的能力受限于三件事：

第一，模型本身的推理能力。工具只能提供信息，不能替模型做判断。如果模型无法正确理解任务，再多的工具也只会让它更快地跑偏。

第二，工具的覆盖面。Agent 只能在工具允许的范围内行动。没有搜索工具就无法获取实时信息，没有文件工具就无法修改代码，没有数据库工具就无法查询业务数据。

第三，上下文窗口。每一轮观察、思考和工具结果都会占用上下文。长任务必须考虑裁剪历史、压缩结果或把中间产物落盘，否则模型很快就会忘记早期的关键信息。

## 常见误区

最常见的误区是把 Agent 等同于“多调几次 LLM”。如果只是把上一轮输出原样塞回下一轮输入，而没有结构化的状态、明确的停止条件和可控的工具边界，那么得到的只是一个容易失控的对话，而不是 Agent。

另一个常见误区是过度依赖单次 Prompt。很多人希望用一段极长的提示词让模型一次做对所有事情，但真实任务往往需要分阶段验证。与其追求一次成功，不如把任务拆成可检查的步骤，每一步都能被独立验证。

## 在本教程中的位置

在教程前几课里，我们从最简单的 API 调用开始，逐步加入多轮对话、工具调用、状态维护、ReAct 循环和 workflow 编排。每一步都是在补齐上面四个部分中的某一块。理解了这个框架，再去看具体的代码实现，就会发现不同 Agent 框架之间的差异其实都发生在“运行时如何组织循环”这一层。
