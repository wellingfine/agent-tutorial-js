# Workflow

Workflow 关注的是稳定、可控、可解释的流程编排。它把任务的推进路径提前固定下来，模型只在每个阶段内部做局部决策，而不是自由决定下一步做什么。

## 典型的阶段划分

和 ReAct 自由循环不同，Workflow 会提前定义好阶段，例如：

- classify：判断任务类型。
- inspect：读取上下文。
- plan：生成计划。
- apply：执行修改。
- verify：验证结果。
- report：总结输出。

每个阶段都有明确的输入和输出。上游阶段的输出就是下游阶段的输入，阶段之间通过结构化数据而不是自然语言传递信息，这样可以降低模型误读上游结果的风险。

## Workflow 与 ReAct 的取舍

Workflow 更适合流程边界清晰、步骤可预期的任务。ReAct 更适合开放问题和需要模型自主探索的任务。

判断标准其实很简单：如果你能自己把这件事的标准操作步骤写出来，那就应该用 Workflow；如果你写不出来，只能靠临场判断，那才需要 ReAct 的自由度。

Workflow 的优势是可复现和可审计。同样的输入走同样的路径，出问题时能定位到具体阶段。ReAct 的优势是灵活，但代价是每次运行路径都可能不同，排查问题时需要依赖完整日志。

## 阶段失败如何处置

Workflow 的每个阶段都应当定义失败语义。常见做法有三种：

重试：适用于偶发失败，例如网络抖动导致的工具调用超时。重试需要限制次数并加入退避。

降级：适用于某一阶段无法完成时仍能产出部分价值，例如 verify 阶段跳过自动验证、改为提示人工确认。

中断：适用于前置条件不满足的情况，例如 inspect 阶段发现目标文件不存在，此时继续执行 apply 没有意义，应当直接终止并给出明确原因。

## 状态与幂等

Workflow 通常会跨越多次调用，因此需要显式管理状态。状态里至少应保存当前阶段、已完成阶段的产物以及失败计数。

幂等性同样重要。如果 apply 阶段执行到一半失败，重跑时不应重复写入已经完成的部分。工程上的做法是为每次运行生成唯一标识，并在写入前检查该标识是否已经处理过。

## 二者如何组合

在真实项目中，二者经常组合使用：Workflow 负责外层流程，ReAct 可以作为某个节点内部的决策策略。

例如一个代码修改任务，外层用 Workflow 固定 classify、inspect、plan、apply、verify、report 这条主线，而在 plan 阶段内部允许模型用 ReAct 的方式多次读取文件、检索依赖，直到对修改方案有足够把握。

这样的组合既保住了整体的可控性，又给真正需要探索的环节留出了灵活度，是实践中较为稳妥的方案。
