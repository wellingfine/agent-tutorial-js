# ReAct Agent

ReAct 是 Reasoning and Acting 的缩写，核心思想是让模型在推理和行动之间交替进行。它不要求模型一次性给出完整答案，而是允许模型先想一步、做一步、再看一步，逐步逼近目标。

## 一个典型 ReAct 循环

一个典型 ReAct 循环包括：

1. 观察当前任务和上下文。
2. 思考下一步应该做什么。
3. 如果需要外部信息或外部动作，就调用工具。
4. 读取工具结果。
5. 决定继续调用工具，还是输出最终答案。

这五步会不断重复，直到模型认为可以给出最终答案，或者达到预设的最大轮数。

## Thought、Action 与 Observation

ReAct 的每一轮通常由三段组成：

Thought 是模型的内部推理。它回答的问题是“我现在知道什么，接下来缺什么”。这一段不产生外部副作用，但决定了后续动作的质量。

Action 是模型决定执行的具体动作，通常表现为一次工具调用，包含工具名和参数。好的 Action 应当是最小且明确的：一次只做一件事，参数清晰无歧义。

Observation 是工具执行后返回的结果。它会被追加进消息列表，成为下一轮推理的依据。Observation 必须忠实反映真实执行结果，包括失败和报错，否则模型会基于虚假前提继续推理。

## 为什么要保存 messages

在代码实现上，ReAct Agent 往往需要保存 messages，因为 messages 里包含用户目标、模型历史回复、工具调用参数和工具执行结果。

Thought、Action、Observation 三段之所以能串起来，靠的就是这条不断变长的消息列表。模型每一轮看到的都是完整历史，因此它知道哪些尝试已经做过、哪些工具返回了什么，从而避免重复劳动。

这也带来一个现实问题：历史越长，上下文压力越大。工程上常见的做法是对早期的 Observation 做裁剪或摘要，只保留与当前决策相关的部分。

## 停止条件非常重要

ReAct 的关键不是某一个固定 prompt，而是让模型拥有“观察、行动、再观察”的闭环能力。但闭环必须有出口，否则就会变成无限循环。

常见的停止条件有三类：模型主动输出最终答案、达到最大轮数上限、单次动作连续失败超过阈值。生产环境中至少要设置轮数上限，这是防止失控兜底的最后一道防线。

## 常见的失败模式

第一种失败模式是空转：模型反复调用同一个工具、传入几乎相同的参数，却始终得不到新信息。这通常意味着 Thought 环节没有真正更新判断。

第二种失败模式是过早收敛：模型只调用一次工具就匆忙给出答案，跳过了必要的验证步骤。适当在提示词中要求“先确认再回答”可以缓解这个问题。

第三种失败模式是错误累积：早期一次工具调用参数写错，模型基于错误的 Observation 继续推理，最终答案与错误前提一脉相承。因此，对工具参数做校验、对工具结果做结构化处理，比事后修补 Prompt 更有效。

## 适用场景

ReAct 适合开放性强、路径不确定的任务，例如排查一个未知原因的故障、调研一个不熟悉的领域。这类任务无法预先写死步骤，只能让模型边探索边决策。反过来说，如果流程本身是固定且可预期的，那么使用后面会讲到的 Workflow 会更加稳定可控。
